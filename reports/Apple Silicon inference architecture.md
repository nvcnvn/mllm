# Memory bandwidth decides where your tokens run

On a Mac mini M4 Pro, the CPU, GPU and Neural Engine draw on one 273 GB/s LPDDR5X pool. Single-stream decode is limited by how fast weights and KV cache can be streamed from that pool, and the GPU alone already reaches about 70–85% of it. Splitting one stream's decode across units therefore cannot make it faster. Your first reason for building your own engine (running CPU, GPU and ANE together) only pays as *overlap*: a compute-bound phase on one unit (prefill of the next request, a drafter, sampling) runs while bandwidth-bound decode continues on the GPU. Even that is unproven on Apple Silicon. The only published ANE-prefill + GPU-decode work was slower than plain MLX for a single request and never measured true concurrency. Your second reason (a custom KV/attention cache) is the stronger one. MLX's KV cache grows by copying, batches by padding, runs attention unfused over quantized KV, and has no paged or varlen attention, and the MLX maintainers said in September 2026 that they will not add paged attention soon. The plan below is a GPU-first Metal engine. Its core is a preallocated, paged, q8-capable KV arena with split-KV flash decode and a prefix tree, plus the per-token overhead discipline that native runtimes use to beat MLX by 5–15% on 3B+ models. CPU and ANE offload should be added only after a short set of bandwidth and contention measurements, none of which anyone has published for this machine, shows they help.

## 273 GB/s, shared three ways, sets every ceiling on the M4 Pro

The M4 Pro's memory is **LPDDR5X-8533 on sixteen 16-bit channels (a 256-bit bus), giving 273 GB/s**. Every compute unit on the die reads that one pool through the SoC fabric and a shared System Level Cache ([Wikipedia M4](https://en.wikipedia.org/wiki/Apple_M4); [MacRumors](https://www.macrumors.com/2024/10/29/apple-announces-m4-pro-chip)). "Unified" means CPU and GPU see the same physical pages. A weight file mmap'd from disk can be wrapped as a GPU buffer with no copy, but the pointer and length must be page-aligned and inside one VM region ([Apple Metal docs](https://developer.apple.com/documentation/metal/mtldevice/makebuffer(bytesnocopy:length:options:deallocator:))). Apple Silicon uses 16 KB pages, and the GPU's MMU maps only 16 KB pages ([Asahi Linux AGX docs](https://asahilinux.org/docs/HW-AGX)). Unified memory does not give you free coherency. The CPU must not mutate a buffer that an in-flight command buffer is reading, so synchronization stays explicit.

The GPU also cannot use all 64 GB. Metal reports a budget via `recommendedMaxWorkingSetSize`, and the community-observed default is about 75% of RAM, roughly **48 GB on a 64 GB machine**. Apple has not documented this figure. `sudo sysctl iogpu.wired_limit_mb=<MB>` raises it until the next reboot ([mlx-lm #883](https://github.com/ml-explore/mlx-lm/issues/883); [devnote](https://github.com/ivanopcode/devnote-override-macos-metal-vram-cap)). mistral.rs states the same arithmetic plainly: "On a 64 GiB Mac … mistral.rs plans to use at most 48 GiB" ([mistral.rs paged-attention docs](https://github.com/EricLBuehler/mistral.rs/blob/master/docs/src/content/docs/guides/perf/paged-attention.mdx)). Your weights plus KV arena must fit in that budget.

The three compute units look very different on paper. Only the GPU has an open, documented, high-bandwidth programming path.

| Unit | Peak matrix throughput | How you reach it | Hard constraints |
|---|---|---|---|
| GPU, 20 cores (Apple family 9) | ~6–8 TFLOPS FP16 = FP32 (estimate; Apple publishes none). PP512 implies ~6.2 TFLOPS achieved | Metal / MSL, `simdgroup_matrix` 8×8 | No int8 dot product. No Neural Accelerators (those arrive with M5). TensorOps `matmul2d` runs on shader cores at only 1.05–1.21× the legacy path |
| CPU, 10P + 4E | ~2 TFLOPS FP32/FP16/BF16 and ~4 TOPS INT8 *per P-cluster* SME unit, measured on base M4 | SME/SME2 (architectural ISA), or AMX via Accelerate | One matrix unit per cluster, so more threads on a cluster add nothing. M4 Pro cluster count unverified |
| ANE, 16 cores | "38 TOPS" (INT8 marketing). ~19 TFLOPS FP16 measured | Core ML, or private `_ANEClient` / `_ANECompiler` APIs | Static shapes, fixed `[1,C,1,S]` fp16 IOSurface layout, ~32 MB SRAM, ~1 GB chunks, ~119 compiles per process |

Sources for the table: GPU microarchitecture from [metal-benchmarks](https://github.com/philipturner/metal-benchmarks) (M1/M2) and [Apple's M3 GPU tech talk](https://developer.apple.com/videos/play/tech-talks/111375/). The achieved-TFLOPS figure is derived from [llama.cpp #4167](https://github.com/ggml-org/llama.cpp/discussions/4167). TensorOps on M4 from [Rigel, arXiv 2606.12765](https://arxiv.org/html/2606.12765v1). SME from [Uni Jena SME microbenchmarks](https://scalable.uni-jena.de/opt/sme/micro.html). ANE from [Orion, arXiv 2603.06728](https://arxiv.org/html/2603.06728) and [Anemll](https://github.com/Anemll/Anemll).

Three microarchitectural facts drive kernel design on the GPU. First, **FP16 runs at the same FLOP rate as FP32** (256 FLOP per core-cycle), and there is no fast INT8 or BF16 path. A 4-bit weight therefore saves bandwidth only: it is dequantized to FP16/FP32 in registers ([metal-benchmarks](https://github.com/philipturner/metal-benchmarks)). Second, M3/M4 "Dynamic Caching" turns the register file and threadgroup memory into one dynamically allocated on-chip cache. Register-heavy kernels no longer collapse occupancy as they did on M1/M2, and the hardware throttles occupancy itself when the working set would spill ([Apple tech talk 111375](https://developer.apple.com/videos/play/tech-talks/111375/)). Third, measured SLC bandwidth is about 2× DRAM bandwidth on M1/M2 ([metal-benchmarks](https://github.com/philipturner/metal-benchmarks)). No primary source gives the M4 Pro SLC size. One community estimate says 32 MB.

The CPU side is more capable than most engine designs assume. On base M4, one P-core issuing SME `FMOPA` reaches **2,008 GFLOPS FP32 and 4,020 GOPS INT8**. But 1–4 threads on the same P-cluster total the same ~2 TFLOPS, because the cluster shares one matrix unit. Adding an E-core thread lifts the total to ~2.37 TFLOPS. Neon FMLA reaches only 107 GFLOPS per core ([Uni Jena](https://scalable.uni-jena.de/opt/sme/micro.html)). If the M4 Pro's 10 P-cores form two clusters with one SME unit each, the CPU offers roughly 4 TFLOPS, about half the GPU's FP16 peak. That cluster topology is not confirmed by any source. SME widening FP16 runs at the FP32 rate, so INT8 (W8A8) is the CPU's best case. Each `SMSTART`/`SMSTOP` costs enough that kernels need long streaming-mode regions: 8 FMOPAs per region reach 434 GFLOPS, and 128 per region reach 1,947.

The ANE is the most tempting unit on paper and the hardest to use in practice. Orion measured **~19 TFLOPS FP16** on the M4 Max's ANE, two to three times the M4 Pro GPU's estimated peak. It also found that INT8 is dequantized before compute, so INT8 saves bandwidth but not cycles. maderix/ANE disputes this with a measured 1.88× INT8 speedup, and the conflict is unresolved ([Orion](https://arxiv.org/html/2603.06728); [maderix/ANE](https://github.com/maderix/ANE)). Several constraints apply. All I/O is fp16 in a fixed IOSurface layout. Shapes are static, so prefill runs in buckets of 32–1024 tokens. A 32,000-channel vocab projection is rejected. Each dispatch costs ~0.095 ms, and an IOSurface round trip ~2.3 ms. Weights are baked in at compile time (4.2 s to recompile, 494 ms with weight patching). Compiles silently fail after ~119 per process ([Orion](https://arxiv.org/abs/2603.06728)). Anemll handles this by splitting models into chunks of ≤ ~950 MB (embeddings, FFN chunks, LM head) and moving argmax into the model to shrink ANE-to-host traffic ([Anemll calc_chunk_split.md](https://github.com/Anemll/Anemll/blob/main/docs/calc_chunk_split.md)). Achievable ANE memory bandwidth on M4-class chips is unmeasured in every source reviewed. Apple advertises a "higher-bandwidth connection" for the ANE only from M5 Pro/Max ([Wikipedia M5](https://en.wikipedia.org/wiki/Apple_M5)).

## Decode streams weights while prefill burns ALUs

The performance model is simple and well supported. At batch 1, **decode tok/s ≤ 273 GB/s ÷ (bytes of active weights + bytes of KV read per token)**. Prefill is compute-bound once a weight read is amortized over enough tokens. The cleanest evidence comes from llama.cpp's frozen-build table of M-series chips, where the 16-core and 20-core M4 Pro share the same bandwidth. Their decode is identical (Q4_0 TG128 49.6 vs 50.7 tok/s; F16 17.19 vs 17.18). Prefill scales 1.22× against a 1.25× core ratio ([llama.cpp #4167](https://github.com/ggml-org/llama.cpp/discussions/4167)). Apple's own MLX team saw the same split on M5: Neural Accelerators made TTFT 3.3–4.1× faster than M4, but decode only 1.19–1.27× faster, matching the 28% bandwidth increase ([Apple ML Research](https://machinelearning.apple.com/research/exploring-llms-mlx-m5)).

| Model on M4 Pro 20c | Active bytes/token | Bandwidth ceiling | Observed |
|---|---|---|---|
| Llama-2 7B F16 | ~13.5 GB | ~20 tok/s | 17.2 tok/s (~85% of 273 GB/s) |
| Llama-2 7B Q4_0 | ~3.8 GB | ~71 tok/s | 50.7 tok/s (~71%) |
| Llama 3 8B Q4_K_M | ~4.9 GB | ~56 tok/s | ~40–45 expected |
| Dense 32B, 4-bit | ~18–19.5 GB | ~14–15 tok/s | ~10–12 expected |
| Qwen3-30B-A3B 4-bit (MoE) | ~1.9 GB active | ~140 tok/s | 80.7 (llama.cpp) / 83.1 (MLX) / 84.1 (BaseRT), measured on 16c |

Observed rows come from [#4167](https://github.com/ggml-org/llama.cpp/discussions/4167) and [BaseRT, arXiv 2607.00501](https://arxiv.org/abs/2607.00501). Ceilings and "expected" values are derived arithmetic.

The efficiency column matters more than the ceilings. Achieved bandwidth drops from ~85% for F16 to ~71% for Q4_0. The bytes shrink, but the dequant ALU work and fixed per-token costs stay the same. MoE models fall even further short (~58% of the ceiling), because routing, attention and the LM head add overhead that the active-parameter count hides. Larger chips use their bandwidth worse still: Q4_0 decode reaches only ~44% of peak on an M3 Ultra ([#4167](https://github.com/ggml-org/llama.cpp/discussions/4167), derived). The lesson for your engine is that past ~80% of 273 GB/s, the remaining decode gains come from removing fixed per-token cost, not from faster GEMV. BaseRT, a native-Metal C++ runtime with a zero-allocation decode loop, fused operator sequences and CPU–GPU sync amortized over several tokens, beats MLX by **1.35× on Qwen3-0.6B but only 1.05× on Llama-3.2-3B and 1.01× on Qwen3-30B-A3B** on an M4 Pro ([arXiv 2607.00501](https://arxiv.org/abs/2607.00501)). On the models a 64 GB machine is bought for, a better runtime alone buys single-digit percentages.

Fixed per-token cost is real but mostly hidden already. A study of MLX decode on M4 Pro measured ~3.04 µs per GPU dispatch boundary and 0.54 ms of CPU graph build and encode per token. The encode cost is almost fully hidden: pipelined decode took 6.04 ms per token against 6.53 ms synchronous, because mlx-lm builds token t+1's graph while the GPU runs token t. The remaining loss is serialization. Twenty-four *dependent* matvecs ran at 77 GB/s against 114 GB/s for independent ones, and 2 ms of a 6.04 ms token went unexplained by summed op times ([Yemets et al., arXiv 2610.31479](https://arxiv.org/abs/2610.31479)). A CPU–GPU round trip with `waitUntilCompleted` costs ~0.12 ms on an M2 Max ([Apple dev forum 767853](https://developer.apple.com/forums/thread/767853)), so it must never sit inside the per-token loop.

The KV cache is the term that grows. Llama-3-8B-style GQA (32 layers × 8 KV heads × 128 dims × K,V × fp16) costs **128 KiB per token, about 4 GiB at 32k context**. Qwen3-4B costs 144 MiB at 1k tokens and 4.6 GiB at 32k ([arXiv 2610.31479](https://arxiv.org/abs/2610.31479); 8B figure derived). At 32k context, the KV read per token is about as large as the 4-bit weights, so decode roughly halves. The measurements agree. gpt-oss-20B on an M4 Pro drops from ~54 tok/s at 16K to ~33 at 64K, an anecdotal figure ([Hardware Corner](https://www.hardware-corner.net/is-mac-mini-m4-pro-good-for-llms/)). Apple's Core ML Llama-3.1-8B drops from 39.4 tok/s at 128 max context to 21.5 at 8192 ([Apple ML Research](https://machinelearning.apple.com/research/core-ml-on-device-llama)). This is why the attention and cache design is where a custom engine can actually move the needle on this hardware.

The roofline also predicts where spare capacity lies. For a 4.5-bit weight GEMM, arithmetic intensity is about 3.6·M FLOP/byte against a ridge of ~31 FLOP/byte, so **the GPU stays bandwidth-bound until about 8–9 tokens share each weight read** (derived). Verifying 4–8 speculative tokens, or decoding 4–8 concurrent requests, costs almost the same DRAM traffic as one token. At batch 1, the GPU's ALUs are mostly idle during decode. That idle compute, not idle bandwidth, is the real resource your first goal is reaching for. It is also available on the GPU itself, with no cross-unit synchronization.

## MLX nails the GPU fast path and leaves the cache behind

MLX is a NumPy/JAX-style array library with a C++ core and thin Python, C and Swift bindings. Arrays have no device. Each op picks a stream (`mx.cpu` or `mx.gpu`), buffers are never moved, and the scheduler inserts cross-stream dependencies automatically ([MLX unified memory docs](https://ml-explore.github.io/mlx/build/html/usage/unified_memory.html)). Ops are lazy and only record a graph. `mx.eval` and `mx.async_eval` materialize it. `mx.compile` fuses only elementwise and broadcast chains (≤ 11 deep, ≤ 24 inputs), so all the LLM-relevant speed lives in hand-written kernels: `qmv_fast`/`qmv_wide`/`qmm` for quantized matmul, `sdpa_vector` for decode attention, and the "steel" tiled GEMM and attention templates ([MLX compile.cpp](https://github.com/ml-explore/mlx/blob/main/mlx/compile.cpp); [MLX kernels](https://github.com/ml-explore/mlx/tree/main/mlx/backend/metal/kernels)).

Several Metal-backend choices are worth copying outright.

**Buffers and memory.** Every buffer is `StorageModeShared | HazardTrackingModeUntracked`, and MLX does its own hazard tracking. The allocator is a page-rounded, size-bucketed buffer cache with a GC threshold at 95% of the recommended working set ([allocator.cpp](https://github.com/ml-explore/mlx/blob/main/mlx/backend/metal/allocator.cpp)). Weights are wired through several size-capped `MTLResidencySet`s, so that losing residency under memory pressure only re-faults one set ([resident.h](https://github.com/ml-explore/mlx/blob/main/mlx/backend/metal/resident.h)).

**Command submission.** Work goes into a concurrent compute encoder. Command buffers are committed every 40 ops or 40 MB on Pro-class chips (arch suffix `g`) ([device.cpp](https://github.com/ml-explore/mlx/blob/main/mlx/backend/metal/device.cpp)).

**Cross-stream fences.** By default these use `MTLSharedEvent`. An opt-in `MLX_METAL_FAST_SYNCH` mode uses a 4-byte shared counter instead: a GPU one-thread kernel publishes it with a system-scope fence, and the consumer spins on it from the CPU or GPU ([fence.cpp](https://github.com/ml-explore/mlx/blob/main/mlx/backend/metal/fence.cpp), [fence.metal](https://github.com/ml-explore/mlx/blob/main/mlx/backend/metal/kernels/fence.metal)). That spin-fence pattern is the template for any fine-grained CPU↔GPU handoff in your engine.

Two MLX facts bear directly on your reasons for leaving it. First, **MLX already runs CPU and GPU work concurrently on shared buffers**. Each CPU stream has its own worker thread, the GPU runs asynchronously after commit, and the docs show a GPU matmul with a CPU-side chain of small ops halving runtime from 2.8 to 1.4 ms on an M1 Max ([MLX docs](https://ml-explore.github.io/mlx/build/html/usage/unified_memory.html); [scheduler.cpp](https://github.com/ml-explore/mlx/blob/main/mlx/scheduler.cpp)). What MLX lacks is the ANE: `Device::DeviceType` is `{cpu, gpu}` only ([device.h](https://github.com/ml-explore/mlx/blob/main/mlx/device.h)). Its CPU backend also goes through BLAS/Accelerate rather than hand-scheduled SME kernels. Second, mlx-lm's serving loop does *not* overlap phases. `BatchGenerator` alternates a decode step and a prefill chunk serially on one GPU stream ([generate.py](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/generate.py)).

The cache is where MLX falls short. `KVCache` stores each layer as a dense `[B, n_kv_heads, T, head_dim]` tensor. When capacity runs out it allocates another 256-token block and `concatenate`s it, which copies the whole cache every 256 tokens. Batches are left-padded inside one shared tensor, and merging requests pads and concatenates again. `QuantizedKVCache` exists (8-bit, group 64), but per the server docs "attention on a quantized cache is not fused", so it materializes a `prefill_step_size × context_length` score matrix, and it disables batching entirely ([cache.py](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/models/cache.py); [SERVER.md](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/SERVER.md)). A NeurIPS 2026 paper reports that this score-matrix materialization dominates peak prefill memory, and that it outweighs the savings from quantizing KV ([NeurIPS 2026 listing](https://neurips.cc/virtual/2026/170026)). Long-context decode was about half of llama.cpp+FA's speed at 30K–146K tokens on an M3 Ultra in one report. That report predates MLX v0.30.4's faster long-context GQA kernel ([mlx-lm #763](https://github.com/ml-explore/mlx-lm/issues/763)). Most decisively, the maintainers closed an external paged-attention integration in September 2026 with "at the moment we don't plan to support paged attention due to lack of resources" ([mlx-lm #1850](https://github.com/ml-explore/mlx-lm/issues/1850)). They had previously closed PR #2760 and PR #2814 as well ([mlx #2814](https://github.com/ml-explore/mlx/pull/2814)).

Other engines show what the cache design space looks like on Metal today.

| Engine | KV design | Attention over it | Lesson for you |
|---|---|---|---|
| mlx-lm | Contiguous per layer, grow-by-concat (256), left-padded batches | `sdpa_vector`; unfused on quantized KV | Baseline to beat |
| llama.cpp | One unified cell buffer; a cell can belong to several sequences; K/V types f16/bf16/q8_0/q4_0/q4_1/q5_x/iq4_nl; KV shifting for reuse; slot save to disk | `fa_*` and `fa_vec_*` flash kernels *per quantized KV type* | Quantized-KV flash decode is solved; study `fa_vec_q8_0.metal` |
| mistral.rs | Paged block pool, HND `[blocks, kv_heads, block_size, head_dim]`, FP8 KV with per-layer scales, preempt and recompute when full | Native `paged_decode_hnd.metal`, `paged_prefill.metal` | Closest open-source match to the cache you want |
| vllm-metal | Fixed page pool sized by warmup; per-request block tables; prefix caching (including GDN state) | Varlen paged kernel ported from vLLM Triton; prefill and decode packed in one pass | 3.64 s vs 10.99 s (mlx_lm) on a mixed-length 8-request batch |

Sources: [llama.cpp kv-cells](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-kv-cells.h), [llama.cpp arg.cpp](https://github.com/ggml-org/llama.cpp/blob/master/common/arg.cpp), [mistral.rs kernels](https://github.com/EricLBuehler/mistral.rs/tree/master/mistralrs-paged-attn/src/metal/kernels), [vLLM blog](https://vllm.ai/blog/2026-09-22-vllm-metal-v0-28-0).

A fair steelman of staying on MLX: vllm-metal built its paged varlen cache by *keeping* mlx_lm's model layers and replacing only attention. MLX also exposes `mx.fast.metal_kernel` for custom Metal source and `mx.export_function` to run traced graphs from C++ without Python ([REL v0.17.0](https://github.com/ml-explore/mlx/releases/tag/v0.17.0); [REL v0.22.0](https://github.com/ml-explore/mlx/releases/tag/v0.22.0)). Your second goal alone does not strictly require a new engine. What does require leaving MLX is the combination of ANE access, hand-scheduled SME, static per-token command encoding, and full control over the allocator and synchronization. Use MLX as your correctness oracle and performance baseline, and as a quick prototyping surface for cache experiments, rather than as a dependency.

## Heterogeneous execution buys overlap and watts, not bandwidth

The most direct evidence comes from a June 2026 STREAM study on an M4 Pro (14-core CPU, 20-core GPU) ([Alpay & Başaran, arXiv 2606.27098](https://arxiv.org/abs/2606.27098)). The CPU alone sustains **204 GB/s** on a 10-thread triad. A GPU linear copy also drives about **200 GB/s**. When both run together at user-interactive QoS, **the GPU slows by a median 16%**. If the CPU threads run at background QoS instead, the GPU is unaffected, but the CPU stream collapses from 189.8 to 15.6 GB/s: macOS moves those threads to E-cores and drops them from 4.3 to 1.1 GHz. After a GPU kernel touches 512 MiB, the next CPU pass over a 16 MiB working set is 63% slower until the SLC refills. Together these show that **CPU and GPU compete for one ~200–230 GB/s effective pipe**. Running a second decode stream on the CPU, or splitting one stream's layers between CPU and GPU, adds no aggregate bandwidth and taxes the GPU. HeteroLLM's +23.4% decode gain from GPU+NPU on Snapdragon likely reflects a GPU that could not saturate DRAM on its own ([arXiv 2501.14794v2](https://arxiv.org/html/2501.14794v2)). Apple's GPU nearly can.

The ANE evidence is thinner and points the same way. AtomGradient ran five pipelines on an M2 Ultra with Qwen3.5 0.8B–9B ([paper](https://atomgradient.github.io/hybrid-ane-mlx-bench/paper.pdf)). Through **Core ML**, `compute_units=ALL` on macOS 26.3 sent the prefill to the GPU, not the ANE, with measured ANE power ≈0 W; Apple's own Core ML Llama guide likewise targets the GPU for 8B models because decode is bandwidth-bound ([Apple ML Research](https://machinelearning.apple.com/research/core-ml-on-device-llama)). Through the **private API with sequential dispatch**, prefill cost ~42 ms per token. With **batched dispatch** (32 tokens per call), prefill reached 268 tok/s for the 0.8B model, but the GPU was already faster at 28-token prompts (290 vs 237 tok/s) ([batch-prefill paper](https://atomgradient.github.io/hybird-batch-prefill-on-ane/paper.pdf)). The **hybrid ANE prefill + MLX decode** pipeline decoded at 39–54 tok/s against ~61–64 for pure MLX, single-request wall time was 6,050 ms against 3,679 ms, and a mixed-precision cache bridge cost 11–16% of decode in another configuration.

The authors explicitly state they never benchmarked true concurrent execution. The case they make for the hybrid rests on power: ANE prefill drew ~1.8 W against ~62 W for GPU prefill. Orion's GPT-2 124M decode was also slower on the ANE than on the CPU (170 vs 283 tok/s) ([Orion](https://arxiv.org/html/2603.06728)).

This does not kill goal one. It reframes it. Prefill and decode have *complementary* resource profiles: prefill uses ALUs with little DRAM traffic per token, and decode uses DRAM with idle ALUs. The sound version of "prefill on one unit while another decodes" pairs a compute-bound phase on a unit with spare FLOPs against a bandwidth-bound phase on the GPU. The table ranks the candidate pairings by how well the evidence supports them.

| Pairing | Why it could work | Why it might not | Evidence status |
|---|---|---|---|
| GPU decodes request A while the GPU also prefills request B, fused into one batch (chunked prefill) | Prefill tokens ride along on decode's weight reads; no cross-unit sync | Long prefill chunks raise inter-token latency for A | Proven: vllm-metal, mistral.rs, vllm-mlx (4.3× aggregate at 16 requests, [arXiv 2601.19139](https://arxiv.org/abs/2601.19139)) |
| CPU handles tokenization, sampling, grammar masks, n-gram drafting while the GPU decodes | Near-zero bandwidth; hides host work | Cache displacement after GPU phases | Proven pattern (mlx-lm async decode); n-gram drafting gave +13% decode on M3 Max ([arXiv 2610.31479](https://arxiv.org/abs/2610.31479)) |
| ANE prefills request k+1 while the GPU decodes request k | ANE ~19 TFLOPS FP16 on paper is 2–3× the GPU; ~60 W → ~2 W | Static shapes, ~1 GB chunks, fp16 overflow, private API, KV bridge cost, unknown ANE bandwidth draw | Unmeasured concurrently on any Mac; slower single-request on M2 Ultra |
| CPU (SME) prefills, or runs a small drafter, while the GPU decodes | ~2 TFLOPS per P-cluster; INT8 4 TOPS | Steals the GPU's DRAM bandwidth (16%+); SME is an outer-product unit that wastes itself on M=1 GEMV | No LLM study on any Mac |
| GPU prefills a long prompt while the CPU or ANE decodes the other sessions ("the opposite") | Long prefill would otherwise stall other sessions on the GPU | The CPU's 204 GB/s is on par with the GPU's but compute-poor at M=1 (Neon ~0.6 TFLOPS on base M4); contention hits both | No study; plausible only for small or MoE models |
| CPU and GPU split one stream's decode | None on this SoC | Same pipe, plus sync per layer | Contradicted by the bandwidth data |

The decision logic follows. On a single-user box, the only win heterogeneity can offer is **TTFT for a long prompt while another conversation keeps streaming, or power**. GPU-side chunked prefill already gets most of the throughput benefit at zero synchronization cost. The ANE path is the only one that could add *new* FLOPs: on paper it could make prefill up to 2–3× faster than the GPU on an M4 Pro, which is what goal one is really after. That depends on three numbers nobody has published for M4: sustained ANE FP16 throughput on transformer-sized chunks, the DRAM bandwidth the ANE consumes while doing it, and how much it slows concurrent GPU decode. The time window is also closing. M5 Pro GPUs with Neural Accelerators claim up to 3.9× faster prompt processing than M4 Pro ([Apple Newsroom](https://www.apple.com/newsroom/2026/03/apple-introduces-macbook-pro-with-all-new-m5-pro-and-m5-max/)), which on future hardware wipes out most of the ANE's advantage.

If you do mix units, there are four rules. Synchronize with `MTLSharedEvent` or MLX-style shared-counter spin fences, never `waitUntilCompleted`. Amortize every cross-unit handoff over large chunks: HeteroLLM measured ~400 µs GPU–NPU sync on mobile, and Orion ~2.3 ms per ANE IOSurface round trip. Remember that macOS QoS, not core pinning, decides whether a CPU helper protects the GPU's bandwidth or starves itself. Issue SME work from one thread per P-cluster.

## The KV arena is the engine's real reason to exist

Your second goal is where the evidence supports building. The design below combines what has been measured to work on Metal.

**Storage.** Use one preallocated, wired arena instead of grow-by-concat. Size it from the GPU budget after weights load. A 4-bit 32B dense model (~18–19 GB) leaves ~25+ GB of the default ~48 GB for KV. Raise `iogpu.wired_limit_mb` if you need more, as mlx-lm's README advises for large models ([mlx-lm README](https://github.com/ml-explore/mlx-lm/blob/main/README.md)). Allocate it as one `MTLBuffer` or `MTLHeap` in shared storage, untracked, and add it to a residency set. llama.cpp keeps its residency sets alive with a heartbeat thread (default 3 minutes) ([ggml-metal-device.m](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-device.m)). With a fixed arena there are no allocator surprises and no periodic `clear_cache()`.

**Layout.** Use pages in HND order, `[block][kv_head][block_size][head_dim]`, as mistral.rs does on Metal, so a decode SIMD group streams contiguous `head_dim` vectors per KV head. Keep a per-sequence block table. Treat block size as a tuned parameter (16–64 tokens is the prior-art range). No published Metal benchmark compares paged and contiguous decode at batch 1, so measure the block-table indirection cost before choosing small pages. For a single user, one contiguous region per sequence plus a prefix cache captures most of the benefit, and paging pays off mainly once you run concurrent agents ([arXiv 2610.31479](https://arxiv.org/abs/2610.31479), derived).

**Precision.** Store q8 K/V by default, with per-block, per-head scales, and dequantize inside the attention kernel. Never materialize dequantized KV or score matrices. llama.cpp proves the kernel side with `fa_vec_q8_0`/`fa_vec_q4_0`, and mistral.rs offers FP8 E4M3 KV at half the memory of BF16. Since decode reads all of KV for every token, q8 halves the long-context term of the bandwidth equation. No M4 Pro measurement of the q8-vs-f16 decode speedup was found, so this is the first thing your kernel benchmark should show.

**Decode kernel.** Use split-KV flash decode. A FlashInfer-style port measured **up to 1.20× decode on M4 Pro**, rising with context (1.02× → 1.20× on Qwen3-4B). The same kernel was 0.97× on M2, where the extra partials traffic did not pay ([arXiv 2610.31479](https://arxiv.org/abs/2610.31479)). That is a reminder that tuning is per chip. Start from MLX's `sdpa_vector.h` (one threadgroup per head-query, 32 SIMD groups striding keys, online softmax merged through threadgroup memory, function-constant specialization) and add the paged gather and q8 dequant.

**Prefill kernel.** Use tiled flash attention with simdgroup_matrix. Avoid naive fusion: on an M4 Max, a scalar fused FA ran ~9× slower than separate well-tiled GEMMs ([Rigel](https://arxiv.org/html/2606.12765v1)). Study metal-flash-attention's skewed block shapes and intentional register spilling at large D ([metal-flash-attention](https://github.com/philipturner/metal-flash-attention)).

**Reuse.** Put a radix or prefix tree over blocks, with refcounts and copy-on-write (mlx-lm #1849's design), plus disk spill. A persistent conversational cache cut wall time by 33/42/57% at turns 3/5/9 in MLX-LM ([arXiv 2610.31479](https://arxiv.org/abs/2610.31479)). oMLX's SSD-persisted KV reportedly cut repeated-prefix TTFT from 30–90 s to 1–3 s ([yage.ai survey](https://yage.ai/share/mlx-apple-silicon-en-20260331.html)). On a single-user Mac with long agent or system prompts, this is likely the largest wall-clock win you can build.

**Model variety.** Keep fixed-size state separate for sliding-window and recurrent/linear-attention layers. Hybrid models add only 8–16 KiB per token, and Gemma-3-4B's KV grows from 136 to 756 MiB rather than linearly ([arXiv 2610.31479](https://arxiv.org/abs/2610.31479)). Leave hooks for KV pruning, which measured 1.36–1.72× on M4 Pro at 4k context, but evaluate quality first and watch peak memory, which rose by up to 155% at short context.

The cache only pays off inside a disciplined runtime. Five pieces matter most.

**Weights.** mmap the files and wrap them with `newBufferWithBytesNoCopy`. Above `maxBufferLength`, use overlapping buffer views, as llama.cpp does ([ggml-metal-device.m](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-device.m)). Note that MLX itself reads with `pread` into its own buffers ([load.cpp](https://github.com/ml-explore/mlx/blob/main/mlx/io/load.cpp)).

**Quantization format.** Use MLX's affine 4-bit, group 64, fp16 scale+bias (~4.5 bpw). It buys compatibility with the mlx-community catalog. Simple formats (Q4_0, MXFP4) also dequantize and prefill faster on Apple GPUs than K-quants ([arXiv 2610.31479](https://arxiv.org/abs/2610.31479)).

**Per-token encoding.** Encode each token into one to three command buffers with a concurrent encoder, range-based barriers (llama.cpp's `ggml_mem_ranges`), one-step-ahead pipelining, and GPU-side argmax/sampling into a shared buffer.

**Fusion.** Fuse the items on llama.cpp's fusion list (RMSNorm+mul, MUL_MAT+ADD residual, MoE top-k routing and reduce). Skip megakernels: public Metal lacks grid barriers, and one measured megakernel ran 1.8× slower ([arXiv 2610.31479](https://arxiv.org/abs/2610.31479)).

**Prefill GEMM.** Hide it behind a narrow interface, so that a TensorOps/NAX implementation can be swapped in on M5+ hardware. On the M4 Pro it brings nothing: llama.cpp disables the tensor API there because it was "no significant difference" on M4/M4 Max ([ggml-metal-device.m](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-device.m)).

## Measure seven numbers before writing the scheduler

Every claim about heterogeneous execution on this machine rests on numbers that are either from other chips or missing. A week of microbenchmarks settles which version of goal one is worth building. Run each on the Mac mini at a warmed-up GPU clock and report distributions, since Rigel saw bimodal results tied to clock state ([arXiv 2606.12765](https://arxiv.org/html/2606.12765v1)). Watch `powermetrics` throughout. The M4 Pro mini draws ~50 W sustained under combined CPU+GPU load and rarely throttles ([Eclectic Light](https://eclecticlight.co/2025/01/22/m4-pro-full-on-when-cpu-and-gpu-draw-over-50-w-and-how-low-power-mode-changes-that/)).

| # | Measure | How | Decision it drives |
|---|---|---|---|
| 1 | GPU read bandwidth; CPU 10-thread triad; both together at user-interactive and background QoS | Metal read/copy kernel timed with `GPUStartTime`/`GPUEndTime`; STREAM | Expect ~200 / ~204 / −16%. If the concurrent sum is ≤ GPU alone, CPU decode offload is dead |
| 2 | Your 4-bit GEMV at real layer shapes, as % of 273 GB/s | Port MLX `qmv_fast`; bytes ÷ kernel time | Gate: ≥ 80% before building anything else |
| 3 | Fixed per-token cost: empty-kernel round trip, per-dispatch cost, tok/s vs model size | Microbench; `mlx_lm.benchmark` and `llama-bench` baselines at 0.6B / 3B / 8B / 30B-A3B / 32B | Sets how much a static-encoded runtime can gain (BaseRT says 1–35%) |
| 4 | Decode tok/s vs context (1k → 64k) for f16 vs q8 KV, contiguous vs paged, plus attention's share of token time | Your `sdpa_vector`-derived kernel vs MLX vs llama.cpp `-fa` | Picks block size, KV precision, and when split-KV turns on |
| 5 | GPU prefill TFLOPS; SME TFLOPS per thread and per cluster on M4 Pro | Steel GEMM port; SME FMOPA loop with 1–10 threads (confirms cluster count) | Whether CPU prefill or drafting has enough FLOPs to matter |
| 6 | ANE: sustained FP16 TFLOPS on one transformer-layer chunk, dispatch latency, and its DRAM draw | Anemll-converted chunk via Core ML (check it really lands on the ANE with powermetrics), then private API if needed | Whether ANE prefill beats GPU prefill at all on realistic sizes |
| 7 | **The money experiment:** GPU decode tok/s while ANE (or SME) prefills another prompt, plus KV handoff latency | Two processes or threads, shared-event sync | Nobody has published it. If GPU decode loses < ~10% and the prefill rate beats GPU chunked prefill, build the heterogeneous scheduler; otherwise don't |

The build order follows from the gates. First, the GPU-only decode path with the fused 4-bit GEMV, static encoding and the KV arena with q8 and split-KV decode, benchmarked against mlx-lm on the same mlx-community weights. Second, the prefix tree with disk spill and chunked prefill interleaved with decode. Third, CPU-side n-gram drafting and sampling. Last, and only if measurement 7 comes out positive, ANE prefill through Anemll-style chunks. Speculative decoding deserves a test on dense 32B targets, where one ~90 ms step is expensive and the 4-bit ridge (~8 tokens) makes verification nearly free. That is a hypothesis: published Apple results on 4B targets were mostly net-negative end to end, including EAGLE-3 at −16% decode on M4 Pro ([arXiv 2610.31479](https://arxiv.org/abs/2610.31479)).

## Conclusion

The M4 Pro rewards an engine that treats DRAM bytes as its only currency. Weights are a fixed toll per token, already paid at 70–85% efficiency by existing engines. KV is the toll that grows with every turn, and nobody in the MLX ecosystem is optimizing it for you. That makes a custom KV/attention cache (paged, q8, split-KV, prefix-shared, disk-spilled) the part of the plan with clear, cited upside. It also makes "use every unit at once" a narrower goal than it sounds. The CPU and ANE cannot add decode bandwidth. What they can add is spare FLOPs for the compute-bound half of the workload and a large cut in power. The one experiment that would justify the heterogeneous scheduler, concurrent ANE prefill against GPU decode on an M4-class chip, has not been published.

There is also a timing effect to account for. Apple is moving dense matrix throughput into the GPU itself: M5 GPUs have per-core Neural Accelerators, and M6 has a "dual 16-core Neural Engine" ([Apple Newsroom](https://www.apple.com/newsroom/2026/08/apple-unveils-a-more-powerful-mac-mini-featuring-the-all-new-m6-and-m5-pro/)). The ANE-prefill trick buys most on exactly the generation you own, and less on each one after. Build the cache and the GPU path as the durable core. Treat ANE and SME offload as a measured, removable experiment rather than the architecture.
